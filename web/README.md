# PWA «Физуха» — модуль 3000 м

Первый рабочий срез мобильного приложения: первый запуск → анкета → проверка данных → создание цикла →
сохранение → оценка → «План готов» → главный экран «Сегодня».

## Слои

```
engine (src/, публичный API)
      ↓ только через engineGateway
application (web/src/application)   создание цикла, AppState, persistence, UI-state, ошибки, форматирование
      ↓
UI (web/src/ui, web/src/app)        формы, навигация, отображение
```

Правила, которые проверяются тестом `tests/app-boundary.test.ts`:

- модуль `web/src/application/engineGateway.ts` — единственное место, импортирующее engine;
- application-слой не импортирует UI;
- frontend не вызывает внутренние спортивные функции (`generateQueue`, `prescribe`, `initialDose`,
  `classify`, `assess*`) и не пересчитывает спортивные решения.

## Данные

- Ключ `fizuha.activeCycle` — versioned envelope `AppStateV1` (см. `docs/pwa-architecture.md` §4, §8).
  Внутри `cycle.engineState` лежит ровно `serialize()` состояния engine, opaque.
- Ключ `fizuha.questionnaireDraft` — черновик анкеты (не спортивное состояние; нужен, чтобы reload не терял
  ответы, см. `docs/wireframes.md` §0.6).
- Повреждённые или несовместимые данные не «чинятся» и не удаляются: приложение показывает явное состояние
  ошибки загрузки.

## Ситуации между тренировками

| Сценарий | Операция | Что попадает в event log |
|---|---|---|
| Не смогу выполнить | `skipScheduledWorkout(...)` | `WORKOUT_SKIPPED` с датой и типом |
| Просрочена, не выполнял | `skipScheduledWorkout(...)` | `WORKOUT_SKIPPED` с той же схемой, но `cause = PAST_DUE` |
| Перенести | `moveScheduledWorkout(...)` | `WORKOUT_MOVED` с обеими датами |
| Контрольный результат | `submitCheckpoint(...)` | `CHECKPOINT_RECORDED` с предыдущей и новой формой и решением engine |

- Все три операции идут через общий `applyEngineTransition`: сначала application-инвариант, затем engine,
  затем diff, event, сериализация и запись — и только потом результат возвращается в UI.
- **Skip не двигает часы.** Engine при вызове `skipWorkout` списывает все просроченные тренировки, если ему
  разрешено продвинуться до `now`, поэтому операция передаёт состояние на его собственной дате: одно решение
  пользователя разрешает ровно одну тренировку, остальные ждут своих.
- **Чередование сохраняется.** Пока более ранняя тренировка не разрешена, ни результат, ни пропуск, ни перенос,
  ни checkpoint не выполняются (`PENDING_RESULT_OUT_OF_ORDER`, а для записи ещё и
  `WORKOUT_RESULT_BEFORE_SCHEDULED_DATE`).
- **Checkpoint** — отдельный lifecycle-переход, а не результат тренировки: `recordCheckpoint` перезаписывает
  Current Performance, поэтому предыдущее значение снимается до вызова engine; immutable baseline не меняется.
  Операция продвигает часы, поэтому подчиняется INV-1.
- Допустимые даты переноса интерфейс ограничивает только техническими рамками (не прошлое, окно плана, не день
  старта). Восстановление, занятость и недельный лимит остаются правилами engine и отображаются по коду ошибки.
- **Причину пропуска определяет приложение, а не экран.** Операция не принимает `cause`: она выводит его из даты
  самой тренировки и даты устройства (`PAST_DUE` для прошедшей, `VOLUNTARY` для сегодняшней и будущей), поэтому
  подделать запись в журнале невозможно.
- **Просроченную тренировку нельзя перенести** (`PAST_DUE_WORKOUT_CANNOT_MOVE`): её закрывают результатом или
  отметкой «не выполнял». Иначе пропуск можно было бы отложить в будущее в обход INV-1. Решение принимает
  `actionAvailability` в application-слое, а экраны и прямой маршрут `/workout/:id/move` его только отражают.

## Обязательные гарантии

- **Дата устройства реактивна.** `useDeviceDate` обновляет календарный день при возврате в foreground
  (`visibilitychange`, `focus`, `pageshow`) и один раз в локальную полночь по таймеру, без polling. Экран
  «Сегодня», INV-1 и состояния вокруг даты старта пересчитываются сами, а engine-clock при этом не двигается:
  смена отображаемой даты и продвижение плана — разные операции.
- **Создание цикла и обновление цикла — разные события.** `adoptNewCycle` открывает onboarding и вызывается
  только после создания нового цикла; `replaceActiveState` принимает новое состояние действующего цикла
  (обновление плана, а в дальнейшем — результат тренировки, checkpoint, смена цели) и onboarding не трогает.
  Общего метода `adopt` нет намеренно.

- **INV-1.** Пока в очереди есть незакрытые тренировки за прошлые даты, ни одна операция не продвигает часы
  engine. Проверка живёт в `application/invariants.ts` и вызывается из `application/clockOps.ts` — единственного
  места, откуда можно вызвать `replan`. UI не может обойти её, даже если кнопка появится: «План» не предлагает
  действий, которые application-слой всё равно отклонит.
- **Данные не удаляются молча.** Повреждённую запись можно удалить только явным подтверждением в экране ошибки;
  несовместимая версия не удаляется никогда.
- **Нет подмены постоянного хранилища.** Если браузер не даёт сохранять данные, приложение сообщает об этом и
  не начинает подготовку: цикл, который не переживёт перезагрузку, не считается сохранённым. Запись проверяется
  чтением (`saveActiveCycle`), поэтому «тихая» потеря данных тоже распознаётся.

## Закрытие тренировки

```
Today → Workout Details → Внести результат → форма → submit
      → engine.recordResult → новое EngineState → serialize → save → Outcome → Today / План
```

- Результат можно внести только за тренировку, которая уже состоялась: `scheduledDate <= deviceToday`.
  Будущую тренировку запрещает application-guard `assertWorkoutResultAllowed` (код
  `WORKOUT_RESULT_BEFORE_SCHEDULED_DATE`), поэтому ни UI, ни прямой маршрут `/workout/:id/result`,
  ни прямой вызов операции не могут закрыть её заранее. Решение о доступности принимается в одном месте
  (`resultAvailability`) и лишь отражается в интерфейсе.
- `application/workoutResult.ts` — единственная операция записи результата. UI никогда не вызывает
  `recordResult` сам: операция проверяет порядок закрытия (INV-1), отдаёт решение engine, считает
  наблюдаемый diff, сериализует новое состояние и сохраняет его **до** возврата результата. При отказе engine
  или хранилища прежнее состояние остаётся активным и ничего не показывается как сохранённое.
- `application/planDiff.ts` — человекочитаемый diff только по наблюдаемым фактам (фаза, допуск, оценка цели,
  состояние, checkpoint, следующая тренировка, тип/дата/объём/темп, появление контрольной). Причина изменения
  берётся у engine, иначе показывается только факт.
- `application/resultForm.ts` — черновик формы и конвертация в контракт engine: девять полей, доли выполнения,
  отрезки (время + дистанция), отдых, условия. Спортивные диапазоны проверяет engine, структурные ошибки — форма.
- B1: блок отрезков раскрыт при `INTERVALS` или заданном `speedRangeMps`; пустые отрезки не блокируют отправку,
  а показывают утверждённое предупреждение о точности. Черновик ответов хранится отдельно
  (`fizuha.resultDraft`) и удаляется после успешной записи; повторное нажатие «Сохранить результат»
  защищено и не вызывает `recordResult` второй раз.
- Outcome живёт по адресу `/workout/:id/outcome` и после перезагрузки восстанавливается из сохранённого
  состояния engine (оценка, причина, следующая тренировка). Список изменений существует только в сессии
  записи: он не восстанавливается и не выдумывается, а просто не показывается.

невнесённый результат (INV-1). Действия, требующие ввода результата тренировки, помечены как следующий срез.
