# ФИЗУХА — защитные границы недельной нагрузки, этап 1

Дата: 13.10.2026. Ветка: `fix/weekly-load-guardrails`, PR #8.

## Причина

При привычных 2 пробежках и 10 км/нед., длинной 6 км, `canRun3Km=false` и доступности 7 занятий прежний движок назначал 4×5 км и 3×6 км, т.е. 38 км за 7 дней. Это **программный дефект**, а не мнение о спортивном прогрессе.

## Что изменено, без новых процентов прогрессии

1. **Частота пробежек:** доступные дни — верхняя граница календаря; новая частота не больше заявленной фактической. Если истории бега нет (`actualRunsPerWeek=0`), предоставляется максимум один вводный бег/ходьба. Повышать частоту только потому, что есть свободные дни, запрещено.
2. **Ограничитель дистанции EASY / LONG_EASY:** по скользящим семи дням учтены предыдущие **назначенные и завершённые** дистанционные занятия, а также ближайшая очередь, включая переносы. Новое EASY/LONG_EASY уменьшается до оставшегося от привычного километража бюджета. При остатке меньше существующего вводного минимума 1 км назначается REST, а не бессмысленный микроотрезок.
3. **Длинные занятия:** не больше одной `LONG_EASY` на любое скользящее семидневное окно. Второе возможное длинное занятие превращается в обычное EASY; если после ограничения его объём не выше обычного EASY, оно не называется «длинным».
4. **Пропуски и защита:** прошлые пропущенные тренировки не компенсируются; STOP/diagnosticHold по-прежнему запрещают качественную работу. Контракты сохранения и API не меняются.

Численно ограничен **назначенный метраж там, где нагрузка задана в METERS**. У тренировок `INTRO_QUALITY`, `THRESHOLD`, `VO2` основная часть может задаваться **минутами**, а разминка/заминка дополнительно — временем. Превращать их в точные километры без реального темпа неправильно: текущий предохранитель НЕ даёт гарантии полного недельного километража, времени работы или физиологической нагрузки для всех профилей.

## Ограничения

**Это консервативная защита от скачка, не завершённый алгоритм прогрессии.** У начинающего без разрешённых быстрых тренировок объём пока не будет увеличиваться выше исходного километража автоматически. Для задачи достижения норматива это лишь промежуточное состояние. PR не следует считать финальной методикой или немедленно вливать без оценки этого ограничения.

Необходимо отдельно согласовать и реализовать:
- Получение надёжных показателей выполнения: GREEN на предзаполненной анкете без подтверждения дистанции/времени не должен автоматически открывать прибавку.
- Условия роста: достаточное число действительно выполненных недель, стабильная переносимость, отсутствие новых жалоб, правильное восстановление.
- Величину **не более одной переменной за раз**: наращивать сначала частоту *или* расстояние *или* интенсивность, но не всё одновременно. Универсальное «10% в неделю» не является гарантированно безопасным правилом.
- Возвращение после перерыва, при неудачных попытках; отдельные сценарии 0 км привычного объёма и противоречивой анкеты.
- Суммарную недельную нагрузку при интервальных тренировках, заданных минутами.

## Минимальная проверка

```bash
npm test
npm run test:ui
npm run test:e2e
npm run typecheck
npm run lint
npm run build
npm run build:web
```

Тесты `tests/weekly-load-guardrails.test.ts` и исправленный `tests/audit-weekly-load.test.ts` покрывают привычный объём, доступность 1–7, скользящее окно, длинные пробежки, пропуск, возвращение после перерыва, сохранение интенсивной работы. В остальных тестах, которые требуют нескольких подряд доступных слотов, исходную **фактическую** частоту нужно установить равной четырём, иначе входные условия больше не описывают требуемую ситуацию.

## Решение перед объединением

Для полной адаптации нужен утверждённый протокол: **когда** и **на сколько** увеличиваем метраж и/или число тренировок при подтверждённой переносимости; без этого данная ветка является первой защитной ступенью и не должна выдавать неподвижную дистанцию за полноценный адаптивный план.
