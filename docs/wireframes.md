# Wireframes — мобильное PWA «Физуха», модуль 3000 м

Назначение: зафиксировать полный мобильный пользовательский путь как прямое основание для frontend-разработки.
Документ структурный, не визуальный: нет цветов, шрифтов, отступов и pixel-perfect значений.

Основание: commit `ce4b44726e9fbf1e2d4be0d5ff4e75bee4ac9f84`. Источники истины:
`docs/ui-engine-contract.md` (граница UI ↔ engine, публичный API, UI-GAP), `docs/pwa-architecture.md`
(слои, AppState, event log, persistence, INV-1…INV-9), `docs/ui-copy.md` (русские формулировки, B1, B3).
Спортивные решения принимает только engine; ни один экран не рассчитывает нагрузку, темп, фазу, допуск к
целевому темпу или оценку тренировки.

## 0. Как читать документ и общие элементы

### 0.1. Формат экрана

```
### WF-NN — Название

[Entry]                  при каком состоянии открывается
[Верхняя часть]          что в шапке
[Основной блок]          главное содержимое
[Основной CTA]           единственное главное действие
[Дополнительные действия] вторичные действия
[Данные engine]          какие поля публичного API питают экран
[Переходы]               куда ведёт каждое действие
```

### 0.2. ID и состояния

- `WF-NN` — экран. `WF-NN.X` — состояние внутри экрана.
- Состояния **цикла** берутся из `pwa-architecture.md` §3: `ACTIVE`, `AWAITING_FINAL_RESULT`, `COMPLETED`.
- Состояния экрана «Сегодня» производны от данных engine (терминальные признаки описаны в
  `ui-engine-contract.md` §2.4, видимость значений — в `ui-copy.md` §12).
- Состояния онбординга (`FIRST_RUN`, `QUESTIONNAIRE`, `REVIEW`, `ASSESSMENT`, `PLAN_READY`) — локальные
  UI-состояния, спортивного смысла не несут. `PENDING_RESULT` добавлено к перечню задач онбординга как
  обязательное следствие **INV-1**.
- Новых спортивных состояний документ не вводит.

### 0.3. Обязательные правила для всех экранов

1. **INV-1.** Пока существует невнесённый результат за прошедшую дату, ни один экран не вызывает операцию,
   продвигающую часы (`replan`, `skipWorkout`, `applyBreak`, `resolveDiagnostic`, `updateTrainingData`,
   `recordCheckpoint`). Исключение — явное действие пользователя в состоянии `WF-13.C`.
2. **INV-4.** Новое состояние engine сохраняется в хранилище до отображения результата.
3. **INV-5.** Никаких прогнозов будущих тренировок за пределами горизонта, который вернул engine.
4. **B3.** Все формулировки берутся из `ui-copy.md`. Технические коды в обычном интерфейсе не показываются
   (исключение — скрытый debug-режим, `ui-copy.md` §12.3).
5. **B1.** Правила формы результата и блока отрезков — `ui-copy.md` §9.
6. Любой экран ошибки имеет выход: назад, «Обновить» или осмысленный CTA. Тупиков нет.
7. Назад разрешено везде, где действие ещё не отправлено в engine. После успешного вызова engine назад ведёт
   в актуальное состояние, а не к откату.

### 0.4. Общий элемент: ввод времени 3000 м

Формат — `ММ:СС`; для результата длиннее часа допускается `Ч:ММ:СС`. Engine хранит секунды, конверсию
выполняет presentation/application layer: пользователь секунды как основной формат не вводит.

| Состояние | Когда | Что показывает интерфейс |
|---|---|---|
| Пусто | поле не заполнено | плейсхолдер `14:30`; «Продолжить» неактивна |
| Неверный формат | `14.30`, `14:3`, буквы | inline: «Введите время в формате ММ:СС» |
| Невозможное значение | `14:75`, `00:99` | inline: «Такого времени не существует. Проверьте минуты и секунды» |
| Вне диапазона | `0:00` или больше 60 минут | inline по тексту `NUMBER_OUT_OF_RANGE` (ui-copy.md §10.1): «Введите значение от {min} до {max}» |

Клавиатура числовая; минуты и секунды — два поля, автопереход не форсируется.

### 0.5. Общий элемент: представление ошибок

| Форма | Когда применяется | Пример | Возврат |
|---|---|---|---|
| Inline | ошибка одного поля или шага | «Введите время в формате ММ:СС» | пользователь исправляет поле |
| Modal / bottom sheet | ошибка, требующая решения | предупреждение об отрезках (WF-18) | «Отмена» или подтверждение |
| Полноэкранная ошибка | состояние недоступно целиком | WF-31.e | «Повторить» |
| Повтор | операция безопасна для повтора | WF-31.a, WF-31.b | «Повторить» |

Заголовок и текст берутся из ui-copy.md §10 по `error.code`; английский `message` не показывается. Код
доступен только в debug-режиме профиля (ui-copy.md §12.3). Допустимость повтора — ui-copy.md §10.4.

### 0.6. Общие правила шага анкеты (WF-02 … WF-09)

Каждый шаг содержит: заголовок шага; «Шаг N из 8» с прогрессом; краткое описание, зачем спрашиваем; поля с
подсказкой «Что это значит?»; «Назад» и «Продолжить»; состояние валидации.

| Состояние шага | Интерфейс |
|---|---|
| Не заполнен | «Продолжить» неактивна для обязательного поля, под полем — подсказка |
| Заполнен корректно | «Продолжить» активна |
| Ошибка формата | inline под полем, поле подсвечено, фокус переходит к нему |
| Ошибка диапазона | inline по тексту `NUMBER_OUT_OF_RANGE` |
| Ошибка engine после «Рассчитать план» | inline на шаге-источнике (WF-10) |

Введённые значения сохраняются при возврате назад и при перезапуске: черновик анкеты хранится application
layer и в engine не отправляется до действия «Рассчитать план».

### 0.7. Состояния хранения

Пять состояний из `pwa-architecture.md` §8 (INV-4), все — в WF-31: данные загружены локально (WF-31.f),
сохранение прошло (WF-31.g), повреждённое состояние (WF-31.d), несовместимая версия (WF-31.c), цикл только
для чтения (WF-31.h). Миграции данных в UI не выполняются ни в одном из них.

### 0.8. Мобильный приоритет и доступность

- Основной viewport 360–430 px, одна колонка, контент скроллится, основной CTA закреплён внизу.
- Главный CTA всегда текстовый.
- Состояние передаётся текстом и знаком; цвет — только поддержка (`ui-copy.md` §1.2).
- Тап-зоны не меньше 44 px; отступ между ними — не меньше 8 px.
- Формы используют системную клавиатуру; числовой ввод — числовая раскладка.
- Ошибка показывается рядом с полем и связана с ним (`aria-describedby`).
- Важный текст не скрывается только в tooltip: пояснение доступно по «Что это значит?».

## 2. Главный экран «Сегодня» (WF-13)

Экран — renderer состояния, а не один статичный вид. Нижняя навигация: Сегодня · План · История · Профиль.
Главный раздел — «Сегодня»: при активном цикле приложение открывается по умолчанию на нём, и возврат из
любого сценария ведёт сюда.
### WF-13 — Сегодня (рендерер состояний)

```
[Entry]          активный цикл: cycleStatus = ACTIVE, AWAITING_FINAL_RESULT или COMPLETED
[Верхняя часть]  «Сегодня» + дата; справа — этап (ui-copy.md §4); нижняя навигация
[Основной блок]  ровно одно состояние из A–L, выбранное по правилу ниже; состояние задаёт содержимое,
                 но не принимает спортивных решений
[Основной CTA]   зависит от состояния (см. таблицу состояний)
[Дополнительные действия] зависят от состояния
[Данные engine]  decision, queue[], history[], checkpointRequired, finalResultRecorded, deviceToday
[Переходы]       определены в каждом состоянии ниже и в master transition map
```

Порядок выбора состояния строгий (сверху вниз), первое подходящее выигрывает:

```
1. cycleStatus = COMPLETED                       → WF-13.I
2. INV-1: есть невнесённый результат за прошлую дату → WF-13.C
3. deviceToday > raceDate                        → WF-13.H
4. deviceToday = raceDate                        → WF-13.G
5. SAFETY STOP/HOLD                              → WF-13.K (пауза)
6. phase = TAPER                                 → WF-13.F
7. checkpointRequired и очередь допускает CONTROL → WF-13.E
8. есть тренировка на сегодня                    → WF-13.A
9. очередь пуста                                 → WF-13.L
10. иначе                                        → WF-13.B (отдых)
```

```
[Верхняя часть]  «Сегодня» + дата; справа — этап (ui-copy.md §4)
[Основной блок]  карточка тренировки:
                   название типа (ui-copy.md §8)
                   краткая задача (goal)
                   объём (dose + unit), число отрезков, если есть
                   рабочий темп, если speedRangeMps или paceRangeSecondsPerKm заданы
                 ниже: «Следующая тренировка: <дата>» (только если engine вернул её в очереди)
[Основной CTA]   «Открыть тренировку»
[Дополнительные действия] «Перенести» ; «Не смогу выполнить»

[Переходы]       «Открыть тренировку» → WF-14
                 «Перенести» → WF-15

```

## 3. Работа с тренировкой

### WF-14 — Карточка тренировки

```
[Entry]          из WF-13.A / WF-13.E / WF-13.F
[Верхняя часть]  название типа (ui-copy.md §8) + дата; кнопка «Назад»
[Основной блок]  «Как выполнить тренировку» — последовательная инструкция (ui-copy.md §0.1):
                   заголовок «Сегодня: …» → нумерованные шаги (разминка, основная часть, время отрезка,
                   отдых, заминка) → «Как должно ощущаться» словами → пояснение к режиму
                 инструкция строится только из полей Workout; отсутствующие данные не досочиняются
                 RPE не является главным ориентиром: слова из scaleLabels, число — рядом
[Технический блок] ниже, как справочник, блоки показываются только при наличии данных:
                   Цель — goal (ui-copy.md §8.1)
                   Объём — dose (мин или м)
                   Основной режим — main.mode (ui-copy.md §8.1)
                   Отрезки — repeats, repeatMeters, finalRepeatMeters («N отрезков по M м»)
                   Отдых — restSeconds («отдых 90 секунд»)
                   Темп — paceRangeSecondsPerKm / speedRangeMps, форматируется в темп «4:20–4:35 /км»
                   Усилие — targetRpe как «План: 6–7»
                   Подсказки — effortCues (ui-copy.md §8.1)
                   Разминка / заминка — warmupMinutes / cooldownMinutes, только если больше нуля
                   «Почему такой темп?» — anchor (ui-copy.md §8.1, только в подробностях)
                 отсутствующий блок не показывается; разминка и заминка не досочиняются
[Раскрываемое]   «Почему такая тренировка?» — цель (goal), anchor, описание типа; вторично по отношению
                 к инструкции и не требуется для выполнения задания
[Основной CTA]   «Начать тренировку»
[Дополнительные действия] «Перенести» ; «Не смогу выполнить»
[Данные engine]  объект Workout целиком (только чтение)
[Переходы]       «Начать тренировку» → WF-17 (форма результата; отдельной фиксации старта в engine нет)
                 «Перенести» → WF-15 ; «Не смогу выполнить» → WF-16 ; «Назад» → WF-13
```

## 6. Master transition map

Состояния цикла — из `pwa-architecture.md` §3. Состояния «Сегодня» — производные от данных engine
(признаки: `ui-engine-contract.md` §2.4). Состояния онбординга — локальные UI-состояния.

```
FIRST_RUN (WF-01)
   ↓
QUESTIONNAIRE (WF-02 … WF-09)
   ↓
REVIEW (WF-10)
   ↓
ASSESSMENT (WF-11)
   ↓
PLAN_READY (WF-12)
   ↓
ACTIVE ────────────────────────────────────────────── main tab «Сегодня» (WF-13)
   ├─ TODAY_WORKOUT            (WF-13.A) → WF-14 → WF-17 → WF-19.A/B/C → WF-13
   ├─ TODAY_REST               (WF-13.B) → WF-21
   ├─ PENDING_RESULT           (WF-13.C) [INV-1] → WF-17 | WF-16 → replan → WF-13
   ├─ TODAY_CONTROL            (WF-13.E) → WF-22 → WF-23 → WF-13
   ├─ TODAY_TAPER              (WF-13.F) → WF-14 | WF-21
   ├─ TODAY_HOLD               (WF-13.K) → WF-05 → resolveDiagnostic → WF-13
   └─ TODAY_EMPTY_QUEUE        (WF-13.L) → replan(same asOf) → WF-13
   ↓
AWAITING_FINAL_RESULT
   ├─ WF-13.G  RACE_DAY        (deviceToday = raceDate) → WF-24 | «Внести позже»
   └─ WF-13.H  AWAITING        (deviceToday > raceDate) → WF-24
   ↓
COMPLETED (WF-13.I)
   ↓
WF-25 итог цикла → WF-26 история / WF-27 архив → новый цикл → QUESTIONNAIRE (WF-02)
```

Правила переходов:

1. Из `ACTIVE` в `AWAITING_FINAL_RESULT` переводит только наступление даты, не действие пользователя.
2. Из `AWAITING_FINAL_RESULT` в `COMPLETED` переводит только `recordFinalResult`.
3. Переход `COMPLETED → QUESTIONNAIRE` возможен только по явному действию «Начать новый цикл».
4. Обратный переход в онбординг при активном цикле не предусмотрен: изменение данных идёт через WF-29/WF-30.
5. Тупиков нет: у каждого состояния есть минимум один переход, возврат назад не откатывает сохранённое состояние.

## 9. Что решено в этом документе

1. **Объединения экранов:** четыре оценки результата — один экран с четырьмя состояниями (WF-19);
   девять состояний «Сегодня» — один экран-рендерер (WF-13); переходы шагов анкеты — один компонент с восемью
   настройками (WF-02…WF-09).
2. **race day** — состояние WF-13.G экрана «Сегодня» (полноэкранное), а не отдельный маршрут: нижняя
   навигация сохраняется, чтобы не было тупика.
3. **FIN от «Внести позже»** не создаёт тренировку и не меняет план: состояние остаётся AWAITING_FINAL_RESULT.
4. **INV-1** выделен в отдельное состояние WF-13.C с приоритетом выше остальных, кроме COMPLETED.
5. **B1** реализован как WF-17.R + WF-18: заметный блок отрезков, отправка не блокируется, предупреждение
   говорит о точности, прогноз оценки запрещён.
6. **B3** соблюдён: технические коды показываются только в debug-блоке профиля.
7. **Тупики исключены:** у каждого состояния ошибки и пустого состояния есть CTA.

## 10. Открытые вопросы

1. Нужна ли фиксация «старта тренировки» в application layer для истории (engine такого состояния не хранит).
   Решение не блокирует wireframes: WF-14 ведёт сразу в форму результата.
2. Нужно ли показывать пользователю дату предполагаемого начала taper как оценку — сейчас показана (WF-21) с
   оговоркой, что она пересчитывается.
3. Название итогового события: «итоговый забег» или «итоговый старт» (вопрос B3 в `ui-copy.md` §14).
4. Единицы измерения по умолчанию и допустимость темпа вместо скорости — настройка интерфейса, спортивного
   смысла не несёт.

## 11. Final lifecycle — реализованное уточнение

WF-24/25/27/29/30 реализованы: объединённое редактирование цели/даты; финальная форма с фиксированной датой старта; durable completed active → verified archive → clear; список всех архивов и `/history/:cycleId`; новый цикл только после безопасного архива. Race/awaiting CTA работает в день старта и позже независимо от старых pending занятий. INV-1 по-прежнему защищает обычные updates. Детали: [final-lifecycle.md](final-lifecycle.md).
