# Issue #51 — технический эксперимент полного прогнозного календаря

**Статус:** постановка задачи для первого технического этапа. Не production-реализация.
**Базовый коммит:** `1e299b83ddedffafb5e047d6580eba5e6bae4308` (`main` на 21.10.2026).
**Рабочая ветка:** `experiment/issue-51-forecast-spike`.
**Связь:** https://github.com/alexandershelepov-glitch/fizuha-3000m-engine/issues/51

## ЦЕЛЬ

Экспериментально проверить, можно ли получить методически состоятельный, достаточно подробный календарь на весь тренировочный цикл до даты норматива, используя действующий движок как единственный источник спортивных правил.

Нужно сравнить два подхода:
- **A — консервативная проекция:** только реальные подтверждённые основания; будущие тренировки занимают резерв нагрузки и восстановления, но не становятся результатами и не начисляют прогрессию.
- **Б — условный сценарий «при успешном выполнении»:** в полностью изолированной расчётной среде допускаются обозначенные как синтетические успешные тренировки; при контрольном 3000 м нельзя выдумывать улучшение времени, можно использовать только прежний известный результат как явно условный сценарный ввод. Такой прогноз не является реальным допуском к нагрузке.

Не выбирать один подход по умолчанию. Сначала показать результаты и ограничения обоих.

## ИСХОДНЫЕ ДАННЫЕ И ОБЯЗАТЕЛЬНЫЕ ИСТОЧНИКИ

- Актуальный исходный код ветки с базой `1e299b83`, особенно `src/engine.ts`, `src/workouts.ts`, `src/models.ts`, `src/assessment.ts`, `src/weeklyLoad.ts`, `src/validation.ts`.
- Контракт между UI и ядром: `web/src/application/engineGateway.ts`, `web/src/application/appState.ts`, `web/src/application/calendarModel.ts`, `docs/ui-engine-contract.md`.
- Существующие сценарии и данные: `audit/fullCycle12w.ts`, `audit/trainingSimulator.ts` и соответствующие тесты. Использовать их как эталоны и источники профилей; не включать аудиторские модули в production-код.
- Методические ограничения и инварианты действующего движка имеют приоритет над эстетикой календаря.

Исследовать минимум три профиля из `audit/fullCycle12w.ts`:
1. `U1-novice` — без результата 3000 м, не пробегает 3 км непрерывно.
2. `U4-intermediate` — средний уровень.
3. `U5-trained` — подготовленный бегун.

Проверить горизонты **8 и 12 недель** для каждого профиля (итого не менее шести конфигураций на каждый подход). Для изменения даты старта/норматива безопасно использовать профильные фабрики/параметры; явно документировать исходные параметры. Если данных недостаточно для числового темпа или будущего контрольного времени, не придумывать их.

## ЦЕЛЕВОЙ РЕЗУЛЬТАТ

Небольшой запускаемый эксперимент и компактный отчёт в репозитории (предпочтительно в `audit/issue-51-forecast-spike/` либо другом понятном месте).

1. **Сравнительная таблица A/Б** по каждому профилю и горизонту, с указанием:
   - тренировок по календарным датам и неделям; тип, основная доза с единицей измерения, повторения, длина отрезка, пауза, темп и скорость дорожки **только если подтверждены исходными данными**;
   - фазы, контрольные точки, окна обязательной переоценки, ограничения после устаревания результата, TAPER и день норматива;
   - планового недельного объёма (не путать дистанцию основной части с полной тренировкой, резервы с фактическими километрами), количества интенсивных занятий;
   - статуса каждой позиции: выданная реальная очередь, консервативный прогноз, условный прогноз, зависимое от данных/неразрешённое;
   - различий A/Б в контрольные моменты: недели 4, 6, 8, 12 (при наличии).
2. **Машинно-читаемые результаты** (JSON или CSV) и человекочитаемые таблицы Markdown. Сделать их воспроизводимыми из одного явного сценария запуска.
3. **Заключение**: какой подход обеспечивает полезный календарь без ложной достоверности, где данные заканчиваются, что надо минимально выделить в общее API ядра, чем обусловлен каждый существенный разрыв между сценариями.
4. **Предлагаемый интерфейс будущего модуля** (контракты данных, статусы, происхождение условных результатов/зависимостей). Это предложение, не обязательство реализовать production-код сейчас.
5. **Короткий отчёт о фактических проверках**, файлах и выявленных ограничениях.

Календарь на 12 недель не обязан содержать выдуманную прогрессию: отсутствие законного назначения или неизвестный темп следует отражать честно. Цель эксперимента — оценить информативность обоих способов, а не любой ценой заполнить пустые клетки.

## ГРАНИЦЫ САМОСТОЯТЕЛЬНОСТИ

Исполнитель самостоятельно выбирает реализацию экспериментальных скриптов, структуру отчёта и порядок проверки. Может добавлять код и тесты эксперимента **только в отдельной ветке**.

Если консервативная проекция требует выделения общего контекста планирования (будущие брони отдельно от подтверждённых фактов), разрешается создать минимальный **экспериментальный** адаптер. Если без изменения production-файлов честный тест невозможен, **не переписывать ядро**: описать конкретную техническую границу, предложить минимальное изменение интерфейса и доказать её существующими тестами/диагностикой. Не выдавать повторение первой недели за полноценное многонедельное прогнозирование.

По окончании можно открыть **draft PR** из экспериментальной ветки в `main` исключительно для обсуждения; не сливать PR без отдельного решения.

## ОГРАНИЧЕНИЯ

- Не изменять `main`, чужие ветки, публикации и пользовательские данные.
- Не менять существующие правила методики, лимиты недельного объёма, интенсивности, восстановления, контрольных занятий, обратной связи, TAPER, допуски или критерии прогрессии.
- Не менять анкету, интерфейс PWA и пользовательский календарь на этом этапе.
- Не создавать второй самостоятельный спортивный планировщик, не копировать таблицы методических решений в UI или в эксперимент в обход ядра.
- Не смешивать синтетическую обратную связь с настоящими `EngineState.history`, `skippedWorkouts`, `appState.events`, `localStorage` или действующей очередью.
- Не показывать прогнозное задание как разрешённое к выполнению только потому, что модель ранее виртуально «успела» подтвердить его.
- Сценарный успешный `GREEN` / `feedbackConfirmed=true` — это предположение **только модели Б**, не доказательство реальной переносимости.
- Контрольный тест будущей даты не может молча улучшать или освежать реальный результат. Для U1 не выдумывать время первого 3000 м и не подтверждать способность пробежать 3 км.
- Не использовать обычный `replan` для простого проматывания будущего без объяснения накопленных пропусков, устаревших контрольных результатов и режимов `HOLD_DIAGNOSTIC`.
- Не импортировать аудиторский симулятор в production `src/`.

## ПРОВЕРКА

Добавить адресные автоматические проверки там, где возможно, и явно отделить выполненные проверки от рассуждений:
- Исходный переданный `EngineState`, сериализованное содержимое, очередь, история, пропуски, `asOf` и приложение не изменяются после многонедельного просмотра; проверить побайтовую неизменность исходного `serialize(state)` и/или структурную идентичность.
- Два расчёта с одинаковыми входами полностью одинаковы, независимо от повторного просмотра.
- Ни одна обычная тренировка не оказывается в день норматива и позднее.
- Ни одна будущая запись не является реальным `HistoryEntry`; идентификаторы и статусы позволяют отличать плановые позиции от результатов.
- Для модели А будущие брони учитывают нагрузки между неделями, но не начисляют `successStreak`, `easyProgression`, `qualityRotation` как подтверждённый успех, новые допуски и «омоложение» измерений.
- Для модели Б каждый гипотетический результат явно маркирован, не проникает в реальное состояние; скорость 3000 м без внешнего подтверждения не улучшается.
- Не нарушаются ограничения rolling 7 days, предельные интенсивности, восстановление, TAPER и структура длительной тренировки.
- Для новичка без измеренного результата нет выдуманного числового темпа и фиктивно открытых быстрых тренировок.
- Честно отражён случай, когда за обязательной контрольной точкой / при устаревшем измерении консервативная проекция не может предписать интенсивную тренировку.
- Результаты можно проверить командами из README эксперимента; выполнить `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` в доступной среде (если невозможно — указать почему). При изменениях в общем коде расширить соответствующие регрессии.

## КРИТЕРИЙ ГОТОВНОСТИ

Эксперимент готов, когда для трёх профилей и двух горизонтов доступны **фактически рассчитанные** сопоставимые таблицы A/Б, результаты повторяемы, реальные состояния доказуемо неизменны, а вывод основан на показанных данных. Все найденные ошибки реализации эксперимента должны быть исправлены и проверки повторены.

Если построить полезный консервативный прогноз при существующем API невозможно, это не повод создавать ложный календарь. В таком случае задача выполняется как **доказанный отрицательный результат**: приложить воспроизводимый минимальный пример препятствия, проверенные ограничения и самый узкий следующий API-шаг. Не утверждать, что обе модели работают, если работает одна.

В конце — краткий отчёт: что добавлено, какие таблицы получены, какие тесты запущены, что не доказано и какая архитектура рекомендована для следующего шага.

**Не переходить** к production-календарю, правкам расписания или слиянию в `main` в рамках этого задания.
