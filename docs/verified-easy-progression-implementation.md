# Проверяемая прогрессия лёгкого бега — эксперимент v1

Ветка `feat/verified-easy-progression` (PR #11), поверх `design/verified-load-progression` / PR #10 и защитного PR #8. **`main` не изменён.**

## Что уже реализовано в коде

- Профиль сохраняет **фактическую историю** `averageWeeklyKm4Weeks` и `actualRunsPerWeek`, не переписывая их из предположений приложения.
- Состояние содержит необязательный для старого v1 `easyProgression.approvedMetersPer7Days`. Старая сохранённая версия инициализируется исходным бюджетом без начисления прибавок за прошлые тренировочные отчёты.
- Поле `feedbackConfirmed` в `WorkoutResult` становится `true` только если человек специально выбирал **фактическое выполнение и тяжесть (RPE)** в форме. При старом черновике эти признаки считаются ложными. Обычный отчет остаётся сохраняемым без подтверждения; классификация GREEN сама по себе не изменена. Но такой GREEN **не повышает беговую нагрузку**.
- Каждые **две полные календарные недели** с даты создания плана рассматривается прошедший блок. Для прибавки обязательны все ожидаемые по расписанию активные занятия, явно подтверждённые ответы, GREEN/GREEN_PLUS, отсутствие пропусков/YELLOW/RED, жалоб, недавнего перерыва, диагностической паузы, RE_ENTRY, обязательного контрольного теста (для тех, кто может 3 км), периода снижения нагрузки перед нормативом.
- В блоке, где уже поднялась доза качественной тренировки, EASY не повышается. **Одновременно наращивать разные параметры не разрешается.**
- Для базы **от 5 км/нед.** прибавка общего утверждённого EASY-бюджета: **500 м** для T0/T1, **1000 м** для T2/T3. Это *тестируемые параметры прототипа*, не научно доказанная универсальная безопасная норма.
- Частота занятий **не увеличивается**. Дополнительная доступность остаётся возможностью выбора дней, не приказом тренироваться больше.
- Для базы **меньше 5 км/нед.** автоматическая прибавка запрещена до отдельной вводной программы ходьба/бег. При `canRun3Km=false` длительные RUN_WALK не присваивают новый результат на 3000 м.
- Пропущенные блоки не начисляются задним числом. Новый большой бюджет не может возникнуть из старого повреждённого сохранения: `deserialize` проверяет новые числовые поля и не удаляет данные при отказе.
- Фактический результат на 3000 м меняется только после внешнего `recordCheckpoint` или `recordFinalResult`.

## Что пока остаётся ограничением

1. Новая часть `feedbackConfirmed` — только подтверждение ответов пользователя, не GPS и не свидетельство фактической дистанции. При полностью заполненных вручную, но неверных данных программа всё равно не может объективно проверить реальное выполнение.
2. Фактическое время EASY не обязано быть измерено; ранее подставленную плановую длительность нельзя трактовать как измерение.
3. Предохранитель считает **метровый EASY/LONG_EASY** по скользящим семи дням. Отдельные упражнения/качество, заданные минутами, не переводятся в километры без измеренной скорости. Полный контроль тренировочной нагрузки и методика ростa качества требуют дальнейшей проверки.
4. У опытных работников повышение quality-дозы может происходить каждую пару успешных качественных тренировок; тогда параллельный рост EASY блокируется, то есть +1000 м не гарантируется через каждые 14 дней.
5. Переход от T0 к непрерывным 3 км сейчас возможен только через отдельный публичный `updateTrainingData` после сознательного подтверждения нового умения. Отдельный UX-сценарий в PWA ещё не разработан.
6. Для человека с базой меньше 5 км вводная лестница бега с ходьбой пока не создана. Это не полностью готовая самостоятельная методика.

## Автоматические сценарии

В `tests/verified-easy-progression.test.ts` включены: две и четыре недели успешной подтверждённой подготовки, невозможность прибавки по предзаполненным результатам, один неполный отчёт, пропуск, YELLOW/RED, нулевая/малая база, наследуемые состояния v1, перерыв, TAPER, отдельно изменяемое `canRun3Km`, **12 недель начинающего**, **8 недель с регулярными пропусками** и **10 недель подготовленного**. Все контрольные результаты в тестах остаются исходными и не моделируют физиологический прогресс.

Только после успешных GitHub Actions и методического анализа этих сценариев PR можно рассматривать для интеграции. Успешный тест означает корректность покрытых переходов кода, не гарантию безопасности и эффективности тренировочного плана у реального человека.

## Интеграционное уточнение 13.10.2026

Прогрессию может разрешить только новый отчёт с **тремя сознательно выбранными ответами**: доля выполнения, тяжесть (RPE) и состояние после тренировки. Технический признак `feedbackConfirmed` не выставляется на основе значения по умолчанию или старого черновика. `EASY`/`LONG_EASY`: RPE 2–4 оценивается как нормальное усилие при отсутствии других проблем. При фактически одном доступном или привычном дне беговой подготовки quality не назначается вместо EASY.
