# Интеграция «ФИЗУХА — 3000 м» (проверочная ветка)

Дата: 2026-10-13. Интеграционная ветка: `integration/3000m-unified-v2`.

## Основной принцип

`main` является базой. Вариант `feat/verified-easy-progression` / PR #11 принят как единственный источник реализованного правила подтверждённого роста EASY. Наследуются защитные ограничения из PR #8 и документированные правила из PR #10. Не складывать разные алгоритмы PR #11 и PR #12: они по-разному моделируют разрешение роста.

## Включённые исправления

- Из PR #13 (включает #9): RPE 2–4 для EASY/LONG_EASY, GREEN при нормальном выполнении и самочувствии, отсутствие INTRO_QUALITY как единственной пробежки при привычной или доступной частоте 1, проверка совместимости защиты недельного объёма и оценки EASY.
- Из PR #12: обязательное явное подтверждение самочувствия для `feedbackConfirmed` и отдельные многонедельные сценарии; на уровне данных сохраняется только формат PR #11, без несовместимого поля `verifiedForProgression`.
- В форме прежние черновики/подставленные значения никогда не подтверждают прогрессию автоматически.

## Что НЕ следует считать готовым

- При базе менее 5 км/нед. пока нет адаптивной вводной лестницы RUN_WALK.
- Переход `canRun3Km=false` к непрерывным 3000 м требует отдельного явного UX-подтверждения.
- Общую километровую нагрузку интенсивных упражнений, заданных минутами, нельзя вывести из фиктивной скорости. Существующие ограничения касаются прежде всего тренировок с точным метражом; полную спортивную безопасность не гарантируют.
- Двухнедельная прибавка +500/+1000 м — прототип правила для проверки, а не универсально научно подтверждённая норма.

## Критерий перед включением в main

Зелёные Node, UI, TS, lint, обе сборки, demo и браузерные E2E в едином CI, отсутствие регрессии 10→38 км, корректные сценарии RPE 4 и STOP, совместимость старых сохранений. Провести обзор итогового PR. Для реальной выдачи планов сотрудникам потребуется отдельная практическая валидация методики.
