# Долгосрочный аудит адаптации: виртуальные 8–12 недель

## Зачем это нужно

Это **испытательный стенд** для алгоритма «ФИЗУХА — 3000 м». Его задача — проверить, как `src/engine.ts` ведёт себя на последовательностях тренировок, а не заявлять, что человек реально станет быстрее. Симулятор использует публичные операции настоящего движка; **нового планировщика нет**. Он не подключается к браузеру, локальному хранилищу, реальным планам сотрудников и текущим датам.

Виртуальный старт: **12.10.2026**, выбран только для воспроизводимости.

## Запуск

Из корня репозитория:

```bash
npm ci
npm run audit:training
npm test
```

Создаются два файла (игнорируются Git):
- `audit/reports/training-audit.md` — сводка и подробные таблицы по неделям/дням;
- `audit/reports/training-audit.json` — машинопроверяемые события, наблюдения, состояния по неделям.

В Pull Request файлы доступны через GitHub Actions → успешный запуск → **Artifacts** → `training-simulator-report`.

## Что проверяется

- Корректное прохождение virtual clock без списания будущих результатов; дата назначений не выходит за день сдачи норматива.
- Соблюдение количества назначений в недельной очереди и отсутствие пробежек при явных `STOP`, `HOLD`, `diagnosticHold`, `relatedYellow`.
- Сохранение журнала настоящих `recordResult` и `skipWorkout`, не превращая пропуск в «тренировочный долг».
- Классификация GREEN/GREEN_PLUS/YELLOW/RED **оригинальным** `src/feedback.ts`.
- Изменения тренировочного объёма, фаз, gate и причины решений в хронологии.
- Реакция на контролируемый 14-дневный перерыв (`applyBreak`) и обязательность явной внешней проверки состояния (`resolveDiagnostic`).
- Состояние финального дня (`recordFinalResult`), после которого очередь тренировок пуста.
- Отдельные признаки несогласованности отчётов и возможных резких одновременных изменений темпа и объёма.

**Не моделируется физиологическая адаптация.** GREEN/RED и повторные тесты — заданные оператором гипотетические входные данные. Внешние 3-километровые замеры в этих сценариях намеренно равны исходным временам. Реальный будущий результат неизвестен. Цель алгоритмического аудита — ловить опасные переходы, деградации и противоречия назначениям. Для реальной методической валидации необходимы пилотные пользователи, фактические отчёты и наблюдение динамики.

## Трактовка результатов

`ERROR` — нарушение проверяемого инварианта или корректности календаря. `WARNING` — потенциальная проблема качества входа или противоречие принципу плавной прогрессии; предупреждение требует отдельной проверки, но само по себе не доказывает баг. `INFO` — техническое наблюдение.

Важно: сводная колонка километража — **сообщённое**, а не назначенное и не реально проверенное расстояние. Значение 0 м может означать незаполненное поле или недостоверные данные. Время/нагрузка также вводятся как тестовые, а не синхронизируются с часами.

После аудита предлагаемые методические изменения разбираются отдельно и не сливаются с `main` автоматически. Симулятор не является медицинским допуском и не гарантирует достижения целевого норматива.
