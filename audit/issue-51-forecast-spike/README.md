# Issue #51 — эксперимент полного прогнозного календаря

Технический spike (ветка `experiment/issue-51-forecast-spike`). Постановка: `docs/issue-51-forecast-spike.md`.
Не production-реализация: пользовательский интерфейс, методика и `main` не затронуты.

## Что здесь

- `forecast.ts` — ядро эксперимента. Две модели прогноза на весь цикл, каждая использует
  исключительно публичные операции/чистые функции движка и никогда не мутирует исходное состояние:
  - **A (консервативное бронирование):** исходное состояние заморожено; каждая будущая цикл-неделя
    генерируется движком (`generateQueue` + `guardWeeklyLoad` со всей цепочкой броней — те же
    публичные функции, что внутри `rebuildQueue`). Будущие назначения резервируют нагрузку и
    восстановление, но **не становятся ни результатами, ни пропусками**: ни одного `recordResult`,
    `skipWorkout` или другого перехода после `createEngine`. Контрольные точки по правилу 21 дня
    отражаются как зарезервированные слоты CONTROL с явной пометкой «измерение не разрешено».
  - **Б (условный сценарий «при успешном выполнении»):** в изолированной копии каждое назначенное
    занятие синтетически «выполняется» GREEN; контрольные 3000 м вводятся только как прежний
    известный результат (улучшение не предполагается); для U1 способность пробежать 3 км НЕ
    подтверждается и время первого 3000 м НЕ выдумывается. Это не допуск к нагрузке.
- Сохранение утверждённой очереди: неделя 1 в обеих моделях отображается из неизменяемого
  снапшота `seed.queue`, снятого на момент расчёта; виртуальное выполнение сценария не может
  изменить представление уже выданных назначений (проверка FS-14 по датам, типам, дозам,
  интервалам, темпам и остальным параметрам).
- Скользящие окна: `sweepRollingWindows` проверяет ВСЕ последовательные 7-дневные интервалы
  прогнозного календаря (включая стыки календарных недель) по бюджету броней и 48-часовому
  восстановлению; во всех 12 прогонах нарушений нет (FS-13).
- `run.ts` — единственный сценарий запуска: пересчитывает 3 профиля (U1/U4/U5) × 2 горизонта
  (8/12 недель) × 2 модели, выполняет встроенный инвариантный свип и пишет артефакты в `results/`.
- `results/forecast-A.json`, `results/forecast-B.json` — машинно-читаемые результаты (строки,
  события, недельные сводки, целостность seed).
- `results/tables.md` — сравнительные таблицы A/Б: недельные сводки, контрольные моменты
  (недели 4/6/8/12), события, полные календари по датам.
- `report.md` — заключение, разрывы A/Б, предлагаемый интерфейс будущего модуля, отчёт о проверках.
- `../../tests/issue51-forecast-spike.test.ts` — адресные автоматические проверки FS-01…FS-12.

## Воспроизведение

```bash
npm run audit:issue51     # артефакты эксперимента (детерминированы, см. FS-02)
npm test                  # весь набор, включая tests/issue51-forecast-spike.test.ts
npm run typecheck && npm run lint && npm run build
```

Исходные параметры: старт цикла `2026-10-12` (как в аудиторских сценариях), дата норматива =
старт + горизонт; анкеты U1/U4/U5 из `audit/fullCycle12w.ts` без изменений (assumptions — в JSON).

## Границы

- Ядро (`src/`) не изменялось; аудиторский симулятор не импортирован в production-код.
- Ни одна синтетическая запись не попадает в реальные `history`, `skippedWorkouts`,
  `localStorage` или действующую очередь: обе модели работают на клонах (доказательство — FS-01,
  FS-05). В модели А после `createEngine` не выполняется ни одного перехода состояния.
- Прогнозные задания не показываются как разрешённые к выполнению: статусы и происхождение
  каждой позиции зафиксированы в данных (`status`, `note`, `syntheticEvaluation`).
- Известная особенность генерации: `generateQueue` вне контекста `history` воспроизводит ритм
  недели только при недельной (понедельной) генерации; ежедневная регенерация на пустой истории
  порождает «фантомные» типы слотов. Поэтому модель А генерируется помнедельно, а флаг контрольной
  точки вычисляется на момент фиксации слота (понедельник − 6 дней горизонта) — это документировано
  в `forecast.ts`. Фиктивная история и фиктивные пропуски не используются.
