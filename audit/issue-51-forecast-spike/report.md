# Issue #51 — отчёт технического эксперимента полного прогнозного календаря

**Ветка:** `experiment/issue-51-forecast-spike` (база `1e299b83`, main не изменялся).
**Запуск:** `npm run audit:issue51` → артефакты в `results/` (JSON + `tables.md`).
**Проверки:** `tests/issue51-forecast-spike.test.ts` (FS-01…FS-12) + полный `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`.

## 1. Что построено

Два прогнозных календаря на весь цикл до даты норматива для трёх профилей (U1-novice, U4-intermediate, U5-trained) и двух горизонтов (8 и 12 недель), итого 12 прогонов. Обе модели двигают только изолированные глубокие копии `EngineState` исключительно публичными переходами движка; ядро (`src/`) не изменялось.

- **Модель А (консервативная).** Каждая будущая позиция явно закрывается `skipWorkout` — тем же переходом, что и автоматический просроченный мисс (согласованное решение 2): занятие занимает резерв нагрузки/восстановления, но не становится результатом и не начисляет прогрессию. Прямой промотка времени через `replan` не используется (она молча копила бы пропуски — постановка это запрещает); каждый пропуск трассирован в данных.
- **Модель Б (условный сценарий «при успешном выполнении»).** В другой копии каждое занятие синтетически «выполняется» GREEN, контрольные 3000 м вводятся только как прежний известный результат (15:30 для U4, 14:30 для U5; улучшение не предполагается). Для U1 способность пробежать 3 км **не** подтверждается и время первого 3000 м **не** выдумывается — контрольных забегов и итогового результата у U1 нет ни в одной модели.

## 2. Главные результаты (см. `results/tables.md`)

**Модель А — честный, но плоский «резервный» календарь.**

- U4/U5: неделя 1 — реально выданная очередь (THRESHOLD + EASY + LONG_EASY с подтверждёнными темпами), недели 2–3 — повтор базовой недели без прогрессии, с недели 4 — обязательное окно контрольной точки (слот CONTROL каждую неделю честно закрывается пропуском, прогрессия невозможна), с недели 7 — результат 3000 м устарел (>42 дней) → доверие LOW, фаза HOLD_DIAGNOSTIC, только EASY. TAPER возникает, день норматива без тренировок. Бюджет заморожен на исходном (U5: 25 000 м на все 12 недель).
- U1: замороженная лестница бег/шаг (этап 0, 2000 м/нед) на весь цикл — без подтверждений движок законно не продвигает ни длительность беговых отрезков, ни объём; темпа нет и быть не может.

**Модель Б — полный содержательный календарь, но каждая позиция предположение.**

- U4 12w: DEVELOPMENT → SPECIFIC (с недели 2) → TAPER; ротация THRESHOLD/VO2/SPECIFIC_3K; дозы растут по правилам движка (THRESHOLD 12→15 мин, SPECIFIC_3K 1800→2200 м); бюджет 19→21 км; контроли в недели 4/7/10 на ровно 15:30; итог 15:30.
- U5 12w: бюджет 25→27 км; SPECIFIC_3K доходят до потолка T3 3000 м; до 48 из 48 позиций имеют подтверждённый темп; контроли на 14:30; итог 14:30.
- U1: объём 2.0→2.4 км/нед, этапы бег/шаг 0→2 — строго по защитным правилам (≤200 м за две недели); темп, контроли, итоговое время отсутствуют (н/д, не выдумано).

**Разрывы A/Б в контрольные моменты** (недели 4/6/8/12, U4 12w): фаза DEVELOPMENT/HOLD_DIAGNOSTIC против SPECIFIC/TAPER; гейт CLOSED против PARTIAL; бюджет 19 000 против 20 000–21 000 м. Все разрывы обусловлены ровно тремя механизмами, которые постановка запрещает считать прогнозом: (1) начисление подтверждённого успеха (`successfulQuality ≥ 2` открывает SPECIFIC, `successStreak` поднимает дозы), (2) fortnightly-пересмотр объёма на верифицированных блоках, (3) «омоложение» измерения контрольной точкой (confidence HIGH против MEDIUM/LOW). Снять любой из них — разрыв исчезает; добавить их в модель А без реальных подтверждений — получится ложный календарь.

## 3. Вывод

**Обе модели работают, и это не противоречие — они отвечают на разные вопросы.**

- Модель А даёт методически состоятельный календарь *резервов и ограничений*: что уже выдано, где обязательные окна переоценки, где план законно заканчивается. Она не предсказывает прогрессию — и по правилам движка не может: прогрессия требует подтверждённых результатов. Как «прогноз» на 8–12 недель она информативна именно честностью границ.
- Модель Б даёт информативный сценарный календарь (структура фаз, ротация, окна контролей), полезный для обсуждения с пользователем, но только с жёсткой маркировкой «условно при успешном выполнении»; её нельзя показывать как план-допуск.
- Рекомендация: в продукте сосуществуют оба режима с явными статусами происхождения; по умолчанию не выбирать один. Отрицательного результата нет — потребность в изменении методики или ядра не выявлена.

**Где данные заканчиваются (зафиксировано в данных, не выдумано):** числовой темп без измеренного результата 3000 м (U1 — весь цикл); любая интенсивная работа за обязательной контрольной точкой при устаревшем измерении (модель А, недели 4+); итоговое время норматива (ни в одной модели не прогнозируется).

## 4. Предлагаемый интерфейс будущего модуля (предложение, не обязательство)

```ts
type ProjectionMode = 'RESERVATION_ONLY' | 'CONDITIONAL_SCENARIO';
type EntryOrigin = 'COMMITTED' | 'CONSERVATIVE' | 'CONDITIONAL' | 'UNRESOLVED';

interface ForecastEntry {
  origin: EntryOrigin;              // происхождение позиции — обязательно
  synthetic: boolean;               // true: результат предположен, не измерен
  assumedEvaluation?: Evaluation;   // только CONDITIONAL
  blockingReason?: ReasonCode;      // например CHECKPOINT_DUE, PERFORMANCE_CONFIDENCE_LOW
  reservationMeters: number | null; // бронь ≠ километры; null = не вычислима без измерения
}

interface ForecastInput {
  mode: ProjectionMode;
  horizonWeeks: number;
  /** Явно перечисленные внешние вводы сценария; источник — только PREVIOUS_KNOWN или EXTERNAL_SCENARIO. */
  externalInputs: {kind: 'CHECKPOINT_3K' | 'FINAL_3K'; timeSeconds: number; source: 'PREVIOUS_KNOWN' | 'EXTERNAL_SCENARIO'}[];
}

interface ForecastResult {
  entries: ForecastEntry[];         // никогда не HistoryEntry
  seedDigest: string;               // serialize(state) до расчёта — контракт неизменности
  seedUnchanged: boolean;           // обязательный постусловный флаг
}
```

Контракты: работа только на клоне состояния; побайтовая неизменность `serialize(state)` — часть ответа модуля; повторный вызов с теми же входами побайтово идентичен; ни одна запись с `synthetic: true` не допускается к записи в `history`/хранилище.

**Минимальный общий API-шаг ядра:** не требуется для честной реализации обоих режимов (эксперимент доказал достаточность существующих переходов). Если понадобится убрать внешний «обход недель», узкое добавление — чистая функция `peekWeek(state, mondayIso)` поверх `generateQueue` без движения часов и побочных эффектов; до такого шага есть смысл дойти только после решения о production-календаре.

Замеченные ограничения (не ошибки реализации, зафиксированы для следующего шага):

1. В модели А пропущенная сессия по правилам движка не требует восстановления (skipped → 0 ч), поэтому интенсивный слот может оказаться на следующий день после прогнозного пропуска; при ежедневном перепланировании типы слотов недели могут пересобираться. Отражено в FS-06 и таблицах.
2. Доказательство «не проникновения» модели Б опирается на изоляцию клонов и проверки FS-01/FS-05; в production-интерфейсе это должно стать машинным контрактом (`seedDigest`), а не конвенцией.
3. Прогнозный объём — это брони (`reservedMetres`), а не километры; в таблицах они явно отделены от бюджета и от дозы основной части.
