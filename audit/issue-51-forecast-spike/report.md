# Issue #51 — отчёт технического эксперимента полного прогнозного календаря (финал)

**Ветка:** `experiment/issue-51-forecast-spike` (база `1e299b83`, `main` не изменялся).
**Запуск:** `npm run audit:issue51` → артефакты в `results/` (JSON + `tables.md`).
**Проверки:** `tests/issue51-forecast-spike.test.ts` (FS-01…FS-14) + полный `npm test`, `typecheck`, `lint`, `build`.

## 1. Что построено

Два прогнозных календаря на весь цикл до даты норматива для трёх профилей (U1-novice, U4-intermediate, U5-trained) и двух горизонтов (8 и 12 недель), итого 12 прогонов. Обе модели работают на изолированных копиях состояния и используют только публичный API движка; ядро (`src/`) не изменялось.

- **Модель А — консервативное бронирование (не моделирование пропусков).** После `createEngine` не выполняется ни одного перехода состояния: ни результатов, ни пропусков — `history`, `skippedWorkouts`, `successStreak`, бюджет и измерение остаются нетронутыми (FS-05). Каждая будущая цикл-неделя генерируется теми же публичными чистыми функциями, из которых состоит реальный `rebuildQueue` — `generateQueue` на замороженной базе и `guardWeeklyLoad` по всей накопленной цепочке броней. Так будущие назначения резервируют нагрузку и восстановление, включая скользящие окна на стыках недель, а сквозная проверка FS-13 подтверждает: все последовательные 7-дневные интервалы в бюджете, качественные занятия разнесены ≥48 часов.
- **Модель Б — условный сценарий «при успешном выполнении».** В отдельной копии каждое занятие синтетически «выполняется» GREEN; контрольные 3000 м — только прежний известный результат (15:30 / 14:30, без улучшения); для U1 способность бежать 3 км не подтверждается, время не выдумывается. Не допуск к нагрузке.

## 2. Устранение трёх замечаний

**Замечание 1 — сохранение утверждённой очереди.** Неделя 1 в обеих моделях отображается из неизменяемого снапшота `seed.queue`, снятого на момент расчёта. Строка `ISSUED` строится из снапшота, а не из живой очереди, поэтому виртуальное выполнение сценария (адаптация доз, ротация, рост бюджета в модели Б) физически не может изменить представление уже выданных назначений. Проверка FS-14 подтверждает идентичность по датам, типам, дозировкам, интервалам (повторы, длина отрезка, финальный отрезок, пауза), темпам, скоростям и остальным отображаемым параметрам, а также что повторная выдача движка побайтово совпадает со снапшотом.

**Замечание 2 — правильная консервативная модель.** Модель А перестроена: вместо `skipWorkout`-прогулки — чистое бронирование без единого перехода. Техническое ограничение существующего API выявлено и обойдено без изменения ядра и без фиктивных данных:

- `generateQueue` вне контекста `history` при ежедневной регенерации порождает «фантомные» типы слотов (свежесгенерированный THRESHOLD в слоте с удерживаемой бронью EASY отравляет соседние слоты внутри одного вызова). Этого состояния (пустая история при длинной удерживаемой очереди) реальный движок не занимает: к моменту горизонта прошлые сессии уже в `history`/`skippedWorkouts`.
- Решение: понедельная (цикл-выравненная) генерация — каждая новая неделя честно воспроизводит ритм выданной (недели 2–4 = неделя 1: THRESHOLD+EASY+LONG_EASY для U4, THRESHOLD+EASY+VO2+LONG_EASY для U5), а флаг обязательной контрольной точки вычисляется на момент реальной фиксации слота (понедельник − 6 дней 7-дневного горизонта), что совпадает с реальной ежедневной очередью движка (CONTROL с недели 5).
- Результат: недели 1–4 — базовый ритм без прогрессии доз; недели 5–7 — зарезервированные слоты CONTROL (окно контрольной точки честно неразрешено); с недели 7 — измерение устарело → HOLD_DIAGNOSTIC, только аэробная работа; TAPER и день норматива без тренировок. Ни одной фабрикованной записи: FS-05 фиксирует ноль `history`, ноль `skippedWorkouts`, нетронутые `skippedIds`/`movedWorkouts`/очередь.

**Замечание 3 — скользящие семидневные окна.** Добавлен сквозной свип `sweepRollingWindows`: для каждого последовательного 7-дневного интервала прогнозного календаря (включая стыки календарных недель) проверяются сумма броней ≤ утверждённого бюджета и ≥48 часов между качественными занятиями. Результат — пусто во всех 12 прогонах обеих моделей (FS-13, JSON-поле `windowViolations`, встроенный свип `run.ts`). Попутно этот свип поймал и помог устранить два реальных дефекта промежуточных реализаций: независимая генерация недель нарушала окна на стыках, а фиксация дозы при входе в горизонт — кратковременные перебюджеты до позднейших ужимок guard.

## 3. Главные результаты (см. `results/tables.md`)

- **Модель А** — календарь резервов и границ: что выдано, что бронируется на базовом уровне, где обязательные контрольные окна (недели 5+), где план законно заканчивается (HOLD_DIAGNOSTIC после 42 дней без измерения). Бюджет заморожен (U5: 25 000 м на все 12 недель). U1: замороженная лестница бег/шаг, 2 000 м/нед, темп отсутствует и не выдумывается.
- **Модель Б** — содержательный сценарий: DEVELOPMENT → SPECIFIC → TAPER, ротация и рост доз по правилам движка (у U5 SPECIFIC_3K до потолка T3 3000 м), бюджет U4 19→21 км, контроли строго на прежнем времени, итог = прежний известный результат. U1: 2.0→2.4 км/нед, этапы бег/шаг 0→2, без темпа/контролей/итога.
- **Разрывы A/Б** в контрольные моменты (недели 4/6/8/12) по-прежнему полностью объясняются тремя запрещёнными постановкой механизмами: начисление подтверждённого успеха, fortnightly-пересмотр объёма, «омоложение» измерения контрольной точкой.

## 4. Архитектурные препятствия

Критичных нет. Один зафиксированный нюанс: контекст ротации/восстановления `generateQueue` читается только из `history`/`skippedWorkouts`/`movedWorkouts`, поэтому честное многонедельное бронирование требует либо понедельной генерации (принято в эксперименте), либо минимального расширения ядра — чистой функции вида `projectWeek(state, fromDate, committed: Workout[]`, которая внутри `rebuildQueue` уже фактически существует и просто не экспортирована. Это необязательный шаг: текущего публичного API достаточно.

## 6. Можно ли переходить к production-модулю

**Да.** Обе модели воспроизводимы одной командой, неизменность реального состояния доказана побайтово, консервативное бронирование реализовано без фиктивных фактов и без изменения ядра, скользящие ограничения проверены сквозняком. Рекомендуемый контур production-модуля — оба режима с явными статусами происхождения (`COMMITTED`/`CONSERVATIVE`/`CONDITIONAL`/`UNRESOLVED`), контракт неизменности `serialize(state)` и запрет записи прогнозных позиций в `history`/хранилище (черновик интерфейса — в предыдущей версии отчёта и в `forecast.ts`, раздел про проекцию). Пользовательский интерфейс и слияние с `main` за рамками этого задания не затрагивались.
