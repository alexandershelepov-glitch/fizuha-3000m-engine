# Ядро адаптивной подготовки «3000 м» v1.0

Изолированное детерминированное TypeScript-ядро. Принимает профиль, явную дату и события; возвращает новое состояние с решениями, reason codes и очередью на следующие семь дней. Нет UI, backend, БД, сети и runtime-зависимостей.

## Запуск и проверки

Node.js ≥22.18, npm. Проверено на Node.js 26.8.1.

```sh
npm ci
npm test
npm run typecheck
npm run lint
npm run build
npm run demo
```

`dist/index.js` и декларации `dist/index.d.ts` — результат сборки для подключения к будущему web/PWA. Тесты используют встроенный `node:test`, исходники TypeScript исполняются через strip-types. Компилятор и ESLint — только dev-зависимости. После установки проверки и demo работают без сети.

## Архитектура

- `src/models.ts`: профиль, снимок результата, обязательные состояния, назначения и обратная связь.
- `src/assessment.ts`: Safety, Confidence, T/Q, Goal Gap/Feasibility, Phase, Target Pace Gate.
- `src/workouts.ts`: начальные дозы, интенсивности, подробное назначение и скользящая очередь; восстановление и недельный лимит.
- `src/feedback.ts`: RED первым, затем GREEN_PLUS/GREEN/YELLOW; причины и характеристики выполнения.
- `src/engine.ts`: переходы, подтверждения нагрузки, прогрессия, перерывы, пропуски/переносы, диагностическая ветка и checkpoint.
- `src/validation.ts`: календарные даты, числовые диапазоны и основные ограничения входа.
- `tests/`: спортивные правила/переходы, 12 сценариев, 15 инвариантов и границы порогов.

Функции не мутируют входное состояние. Время приходит аргументом `YYYY-MM-DD`; внутренние вычисления календарных дней используют UTC и не зависят от часового пояса машины. Скорость — м/с, темп — сек/км; минуты и метры дозы помечены отдельной единицей. Performance всегда отделена от Target.

## Основные вызовы

```ts
import {
  createEngine, recordResult, recordCheckpoint, replan,
  applyBreak, skipWorkout, moveWorkout,
  resolveDiagnostic, updateTrainingData, serialize, deserialize,
} from './dist/index.js';

const state = createEngine(profile, '2026-10-05');
const workout = state.queue[0];
const next = recordResult(state, workout.id, feedback);
const saved = serialize(next);
const restored = deserialize(saved);
```

Полный пример входных данных — `examples/profile.json`; исполняемый пример — `examples/demo.ts`. Схемы `Profile`, `WorkoutResult`, `PerformanceSnapshot` экспортированы из `src/index.ts`.

`recordResult` принимает дату назначения. Для другого дня сначала вызовите `moveWorkout`; два занятия в один день и нарушение восстановления не допускаются. Очередь строится от дня начала цикла, без привязки к дням недели. Каждое обновление проверяет историю и планируемую очередь в скользящем семидневном окне. CONTROL также расходует лимит quality. Пропущенная quality резервирует свой прежний бюджет до выхода из окна: её не заменяют нагрузкой в соседний день.

`recordCheckpoint` — единственный переход изменения точного результата: новый валидный TEST_3K/OFFICIAL_3K. Обычный отчёт CONTROL не доказывает валидность теста. Вызывающий код отвечает за проверку факта дистанции и достоверности результата; ядро проверяет источник, время, дату и состояние Safety. T/Q берутся из фактического тренировочного профиля и не растут от улучшенного времени.

При RED и health YELLOW необходим явный `resolveDiagnostic` с результатом оценки. Обычный GREEN после отдыха не снимает диагностическую блокировку. После перерыва >14 дней две успешные Easy дают запрос диагностики; допустимый новый тест обновляет Performance и завершает RE_ENTRY. Болезнь/травма обрабатываются отдельной диагностической веткой.

`updateTrainingData` обновляет фактическую тренировочную историю и признаки. Поля Performance, breaks и safety защищены отдельными переходами. JSON-сериализация рассчитана на собственное состояние версии 1; это не механизм проверки чужих/подделанных историй или аутентификации.

## Решения и неоднозначности спецификации

Сохранён оригинал задания в `docs/specification.txt`. Все конфликты, незаданные параметры и выбранное минимальное поведение перечислены в `docs/specification-decisions.md`. В частности, сценарий №11 конфликтует с общей таблицей выбора фазы: применён явно документированный консервативный FOUNDATION для LONG_TERM/T1/Q0, без ветвления по персонажу.

Интенсивность Easy описана через усилие: RPE 2–4, разговор полными фразами, контролируемое дыхание; поле темпа отсутствует. Каждая quality содержит дозу основной работы, разогрев/заминку, RPE, диапазон скорости при необходимости, отдых и обратную связь. Для интервалов в метрах последнему повтору разрешена остаточная длина; сумма повторов равна общей дозе.

Прогрессия v1 меняет только объём. Скорость, длина повтора и отдых не прогрессируют одновременно. При переходе PARTIAL → OPEN специфический объём сохраняется. TAPER снижает объём и запрещает развивающую прогрессию, включая тренировки в очереди, дата которых уже попадает в taper.

Сценарные фикстуры дополняют отсутствующие в задании обязательные поля явно: свежий валидный результат, здоровье без stop flags и обычная длинная пробежка. Эти допущения не записываются в бизнес-логику.
